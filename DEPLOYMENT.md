# Deployment Runbook

How to ship the SMS **database**, **backend**, and **frontend** to production.
Point Claude Code at this file ("deploy per DEPLOYMENT.md") and it will follow these steps.

- **Hosting:** Render — one Blueprint ([render.yaml](render.yaml)) defines all three resources
  from repo `nilesh830/school-management-system`, branch `main`, region Singapore.
- **Backend:** Render web service `sms-backend` (Python runtime, gunicorn) — URL shown in the
  Render dashboard, e.g. `https://sms-backend-<hash>.onrender.com`.
- **Frontend:** Render web service `sms-frontend` (Docker: Node build → Caddy). Caddy serves the
  SPA and reverse-proxies `/api/*` to the backend, so the browser only ever talks to the frontend URL.
- **Database:** Render Postgres `sms-postgres`, **schema-per-school** — master tables in `public`,
  each school in its own `school_<slug>` schema (`school_demo`, `school_greenwood_high`).

> **Secrets:** the real production DB URL lives in `deploy/prod.secrets.env` (git-ignored).
> Copy `deploy/prod.secrets.env.example` → `deploy/prod.secrets.env` and fill it from the
> Render dashboard (`sms-postgres` → Connect → **External Database URL**). Never commit it.

## 1. Database changes

Migrations must be applied to **every school schema**, not just `public`. The project's
`flask db-upgrade-all` command handles this: it enumerates active schools from the master
`schools` table and runs Alembic `upgrade head` against each schema (setting `search_path`
per schema — plain `flask db upgrade` only touches `public` and is **not** sufficient).

**When there are new migrations in `backend/migrations/versions/`, run:**

```bash
# read-only: shows schemas, schools, and the Alembic revision per schema — migrates nothing
bash deploy/migrate-prod-db.sh --check

# apply: runs db-upgrade-all across every school schema, with before/after snapshots
bash deploy/migrate-prod-db.sh
```

Equivalent manual command (from `backend/`, using the venv):

```bash
DATABASE_URL="<PROD_DATABASE_URL>" FLASK_APP=run.py FLASK_ENV=production \
  venv/Scripts/python.exe -m flask db-upgrade-all      # venv/bin/python on POSIX
```

**Notes**
- Idempotent: schemas already at head are skipped, so re-running is safe.
- Additive migrations (CREATE TABLE / ADD COLUMN with `server_default`) are safe while old
  code is still serving. For a **new NOT NULL column**, keep its DB `DEFAULT` until the new
  code is live, so in-flight inserts from the old code don't fail.
- New schools created later via `flask provision-school` get the current schema automatically.
- Always run `--check` first and eyeball the before/after `alembic_version` per schema.
- External DB access requires your IP to be in the allowlist (`sms-postgres` → Info →
  Access Control). `render.yaml` opens it to everywhere; tighten it to your own IP.

## 2. Backend

Render auto-builds and deploys `sms-backend` on push to **`main`** (Python runtime,
`buildCommand`/`startCommand` from `render.yaml`). Deploying is therefore a git operation:

```bash
git checkout main
git merge feature/SMS-xxx          # or open a PR and merge
git push
```

Then watch the deploy in the Render dashboard (`sms-backend` → Events/Logs). Render only
routes traffic to the new version once `/api/v1/health` passes, so a broken build keeps the
old code serving.

Backend env vars (set in Render, not in code): `FLASK_ENV=production`, `SECRET_KEY` +
`JWT_SECRET_KEY` (generated by the Blueprint), `DATABASE_URL` (injected from `sms-postgres`,
internal network URL), `CORS_ORIGINS=<frontend URL>`, `PYTHON_VERSION=3.14.0`.

**Order of operations:** if a release has both DB and backend changes, run the DB migration
(step 1) **before** the backend deploy for additive migrations; for destructive ones,
deploy compatible code first. When unsure, migrate additively, deploy, then clean up.

## 3. Frontend

Same model — Render rebuilds `sms-frontend` on push to `main`
(`frontend/Dockerfile`: Node build → Caddy serve on `$PORT`). Push/merge to `main` and watch
the deploy. Frontend env var: `BACKEND_URL=<backend Render URL>` (where Caddy proxies `/api/*`).

Build gotchas already fixed (keep them in place):
- Dockerfile pins npm 11 (`npm install -g npm@11`) so `npm ci` matches the lockfile-v3 `package-lock.json`.
- Caddyfile uses mutually-exclusive `handle /api/*` + `handle` blocks so the SPA fallback can't swallow API calls.
- Caddyfile binds `:{$PORT:80}` — Render sets `PORT` automatically, same as Railway did.

## Quick reference

| Change type | What to do |
|-------------|-----------|
| DB migration | `bash deploy/migrate-prod-db.sh --check` then `bash deploy/migrate-prod-db.sh` |
| Backend code | Merge/push to `main` → Render auto-deploys `sms-backend` |
| Frontend code | Merge/push to `main` → Render auto-deploys `sms-frontend` |
| New school | `flask provision-school --slug … --name … --admin-email … --admin-password …` |

**Verify after deploy:** hit the frontend URL, log in, and exercise the changed feature.
A quick backend health signal: `GET <backend URL>/api/v1/health` returns 200; a new route
returns 401 (deployed) vs 404 (old code still live).

## One-time: cutover from Railway → Render

Done once; kept here for the record and in case it must be repeated.

1. **Merge `render.yaml` to `main`** — the Blueprint must exist on the branch Render connects to.
2. **Create the Blueprint:** Render dashboard → New → Blueprint → connect
   `nilesh830/school-management-system`, branch `main`. Render creates `sms-postgres`,
   `sms-backend`, `sms-frontend`. During creation it prompts for the two `sync: false` vars —
   leave placeholders if the URLs aren't known yet.
3. **Copy the data** (before pointing anything at the new DB):
   fill `deploy/prod.secrets.env` with `RAILWAY_DATABASE_URL` (old) and `PROD_DATABASE_URL`
   (new Render **External Database URL**), then:
   ```bash
   bash deploy/copy-db-to-render.sh     # pg_dump Railway → pg_restore Render, all schemas
   bash deploy/migrate-prod-db.sh --check   # confirm schemas + alembic_version per school
   ```
4. **Wire the URLs** (Render dashboard → service → Environment):
   - `sms-frontend` → `BACKEND_URL` = backend URL (e.g. `https://sms-backend-<hash>.onrender.com`)
   - `sms-backend` → `CORS_ORIGINS` = frontend URL (e.g. `https://sms-frontend-<hash>.onrender.com`)
   Each save triggers a redeploy.
5. **Verify:** log in on the new frontend URL, check attendance/fees/parent portal, and
   `GET /api/v1/health` on the backend.
6. **Decommission Railway:** once Render is verified, delete the three Railway services
   (backend, frontend, Postgres) in project `celebrated-delight` — the Postgres last, after
   confirming the Render copy (and keeping `deploy/railway-prod.dump` as a final backup).
